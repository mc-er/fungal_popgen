Session 2: Nextflow Sarek setup

Introduction

This afternoon we will set up nf-core/sarek and get it running. That is the whole goal: by the time we stop for the discussion session, the pipeline should be running on Kebnekaise and producing output which we will look at tomorrow.

We are deliberately not analysing anything today. Getting a pipeline to start — correct software, correct samplesheet, correct reference, correct cluster settings — is a real part of bioinformatics work, and it is where most of the time goes the first time you meet a new pipeline. Tomorrow morning we look at what came out of it.

NotePlan for the afternoon
  1. Get Nextflow and a container runtime working on Kebnekaise
  2. Run Sarek’s own test profile, to prove the machinery works before any of our data is involved
  3. Look at what Nextflow left behind, so that you can debug a failure on your own
  4. Configure Sarek to submit jobs to SLURM instead of running them where you launched it
  5. Point it at our data and leave it running

Steps 1–3 are the ones that matter. If you get that far and understand what you did, the afternoon was a success

And don’t forget to ask questions if something does not behave the way you expect.

I hope the words Nextflow, nf-core, container and environment manager not new and that you have already gone thought the background pages on Nextflow, nf-core, Containers and Pixi which cover the concepts. This page is only about making it run.

The data

For this session and tomorrow morning we use whole-genome resequencing data from silver birch, Betula pendula:

Salojärvi, J. et al. (2017) Genome sequencing and population genomic analyses provide insights into the adaptive landscape of silver birch. Nature Genetics 49, 904–912.

The reads are public, in ENA study PRJEB14544. We use eleven individuals from it:

Note

The reads you will be given have been subset to two chromosomes. Every step of the pipeline is genuinely identical on a subset — the same tools, the same parameters, the same output structure — so nothing you learn here is specific to the reduced data.

We submit the run to the queue this afternoon and leave it to run overnight, which is how this work is normally done: you do not sit and watch a pipeline. Tomorrow morning the output will be waiting, and that is what we spend the morning on.

NoteSample names: a real-world detail worth noticing

Look at the “original name” column. It contains Pöytä1 and Elimäki1, which have non-ASCII characters, and 21161, 21271 and 2-VR-1-111, which begin with a digit.

Both will cause you trouble. Non-ASCII characters in sample names break tools unpredictably and are miserable to type in a shell; identifiers starting with a digit are mangled by R, and some tools reject them outright. This is exactly the naming problem the Linux page warns about, met in the wild.

So in the samplesheet we use the BioSample accession as the sample identifier. It is stable, unique, ASCII, starts with a letter, and points at a public record anyone can look up. Keep the human-readable names in a separate metadata file, and attach them for plot labels later:

sample,name,run
SAMEA104151691,2-VR-1-111,ERR2026087
SAMEA104151857,21161,ERR2026104
SAMEA104151879,Elimaki1,ERR2026254
SAMEA104151890,Poyta1,ERR2026265
WarningMetadata you do not get

Try looking one of these samples up in the ENA browser. The BioSample record gives you the organism, the submission date and very little else — no sampling location, no population, no provenance. That information is in the paper and its supplementary material, not in the archive.

This is worth contrasting with the fungal dataset we use later in the week, which was chosen precisely because it complies so well with FAIR principles. Both datasets are public. Only one of them is genuinely reusable without reading the paper first.

When you deposit your own data, you decide which of these two experiences you give the next person.

The reference genome

We map against GCA_965285875.1 (dhBetPend1.hap1.1), a chromosome-level assembly produced by the Wellcome Sanger Institute’s Tree of Life programme and released in 2025:

Assembly level Chromosome — all 14 chromosomes assembled
Chromosome names 1 to 14, with INSDC accessions OZ260445.1–OZ260458.1
Chromosome sizes 18.1 Mb (chr 14) to 42.0 Mb (chr 1)
Scaffold N50 28.9 Mb
Total length 403 Mb, in 22 scaffolds, plus mitochondrion and chloroplast
Sequencing depth about 50× long reads
NoteWhy not the assembly from the paper?

The assembly published alongside our reads in 2017 is GCA_900184695.1 (Bpev01): 5 642 scaffolds with a scaffold N50 of about 240 kb. It was a good assembly for 2017, built from short reads.

Eight years of long-read sequencing later, we can do much better, and there is no rule that says you must use the reference the original authors used. A contiguous reference means variants can be placed on chromosomes rather than on anonymous scaffolds, repeats are resolved rather than collapsed, and windowed statistics — Tajima’s D in sliding windows, Fst along a chromosome — actually mean something, because a window can follow a chromosome instead of running off the end of a 240 kb scaffold.

Reusing public reads against a better reference than the original study had is one of the quietly valuable things that open data makes possible.

Two further details matter, and both are about what a reference genome actually is.

First, dhBetPend1 is one individual tree, collected in Surrey in the United Kingdom in 2022. Our eleven resequenced trees are Finnish. The reference is therefore not a neutral backdrop: it is one tree from a different part of the species’ range, roughly two thousand kilometres from the samples we are mapping onto it. We return to what that does to the results tomorrow morning.

Second, this is hap1 of a haplotype-resolved pair — birch is diploid, the assembly separates the two haplotypes of the reference individual, and we use one of them. hap2 exists as a separate accession. So the reference represents a single haplotype of a single tree from a single meadow in Surrey.

What Sarek does

Sarek is an nf-core pipeline for germline and somatic variant calling from short reads. In the configuration we care about it takes FASTQ files and a reference genome, and gives back aligned, duplicate-marked BAM or CRAM files and a VCF.

Stage Tools What you get
Preprocessing FastQC, bwa-mem / bwa-mem2 Aligned reads, read QC
Duplicate marking GATK MarkDuplicates Deduplicated BAM/CRAM
Recalibration GATK BaseRecalibrator Recalibrated base qualities — we will switch this off
Variant calling HaplotypeCaller, FreeBayes, Strelka, … VCF
Reporting MultiQC One HTML report over everything

A human pipeline on a non-model organism

This is the part of the afternoon worth paying attention to, and it is the reason we are running Sarek rather than something simpler.

Tip

There is another pipeline under development that looks like a promising alternative to nf-core Sarek for non-human and non-model species. It lives here: https://github.com/NBISweden/biovat

Sarek is excellent software, but it was written for human clinical genomics and it assumes the world that comes with that: a finished reference genome, decades of curated variant databases, and a patient. A wild birch tree is none of those things. Nothing here stops the pipeline from running, but each assumption has to be recognised and dealt with deliberately — and if you work on wild organisms, you will do this with every pipeline you ever pick up.

What Sarek assumes How it holds for silver birch What we do about it
The reference is one of the standard human builds, shipped via iGenomes There is no iGenomes entry for birch --genome null --igenomes_ignore --fasta <our reference>
A curated set of known variant sites exists (dbSNP, Mills) for base quality recalibration No such set exists for birch. Recalibration would be trained on our own candidate variants, which is circular --skip_tools baserecalibrator
The assembly is chromosome-level, and a sensible WGS intervals file exists Half holds. Our reference is chromosome-level, so the scatter is over a few large intervals rather than thousands of scaffolds — but only because we chose a 2025 assembly instead of the 2017 one, which had 5 642 scaffolds. There is still no human-style WGS intervals BED, so Sarek derives intervals from the reference index Nothing required here. Were the assembly fragmented, you would group intervals with --nucleotides_per_second or disable the scatter with --no_intervals
The organism is diploid This one holds. B. pendula is diploid, 2n = 2x = 28 Nothing to do. Enjoy it — see the note below
Variants can be annotated against a species cache (VEP, snpEff) No cache exists for birch Skip annotation; when we want gene context we intersect regions of interest with a GFF3 by hand
Samples belong to patients, who have a sex and a tumour/normal status A tree is not a patient, and birch is monoecious — individual trees carry both male and female catkins, so sex has no meaning here at all Map each tree onto patient and sample, set sex to NA and status to 0
Important

Notice what the pattern is. Every one of these is a case where a default encodes an assumption, and where accepting the default silently would produce output that looks perfectly normal — plausible file sizes, no error messages — but is not meaningful. Base quality recalibration against your own candidate variants does not crash. It just quietly makes your data worse.

This is the central skill of the course: knowing what a tool assumes, and checking whether your organism satisfies it.

NotePloidy, and why you got off lightly

The germline callers in Sarek assume a diploid genome, and Sarek does not expose a ploidy parameter for them. For silver birch that assumption is correct, so the default does the right thing and there is nothing to configure.

Notice that this is luck, not design. Later in the week we work with a fungus that is haploid for most of its life cycle, and there the same default would produce diploid genotype calls for an organism with one copy of each chromosome — which is why the VCFtools build used for that dataset is a haploid-aware version.

Same pipeline, same default, right answer for one organism and wrong for the other. The default did not change; the organism did. Keep a note of where in a pipeline the ploidy assumption lives, because it is rarely advertised.

Before you start

From this morning you should have:

  • A working login to Kebnekaise
  • Your project ID
  • A directory of your own in the course project storage under /proj/nobackup/<course-project>/analysis/<group-name>
Note

You will run this in your groups. There is no need to run it both of you since it produces the same result.

Work in the project storage, not in your home directory. Nextflow writes an intermediate work/ directory that grows quickly — tens of gigabytes is normal — and a home quota will stop the run dead.

Important

Tomorrow when we have the output it is a good idea to remove the work/ directory we will not need it’s content anymore and it is good practice to free up space.

cd proj/nobackup/<course-project>/analysis/<group-name>
mkdir -p sarek_run && cd sarek_run

Set two environment variables before you launch anything. The first keeps the Nextflow Java process from claiming too much memory on the login node; the second makes containers be downloaded once into a shared cache instead of once per run.

export NXF_OPTS='-Xms1g -Xmx4g'
export NXF_SINGULARITY_CACHEDIR=/proj/nobackup/<course-project>/singularity_cache
Tip

Put both lines in your ~/.bashrc so you do not have to remember them. If you forget the cache variable, every run re-downloads several gigabytes of container images, which is slow for you and unkind to everybody else on the system.

Step 1: Nextflow and containers

Find and load Nextflow:

module spider Nextflow
module load Nextflow/<version>
nextflow -version

Sarek runs each tool inside a container, so you also need a container runtime. On an HPC system that is Singularity or Apptainer, never Docker — Docker needs root privileges, which no shared cluster will give you.

module spider Singularity
singularity --version
Note

If Singularity is available without loading a module, that is normal on many systems. The check is simply that singularity --version answers.

Step 2: the smoke test

Before involving our data, run the test profile that ships with the pipeline. It downloads a tiny dataset and runs the whole workflow on it. If this works, Nextflow, the containers and the filesystem are all fine, and any later failure is about our configuration rather than the machinery.

nextflow run nf-core/sarek -r 3.12.0 -profile test,singularity --outdir test_results
Note

-r 3.12.0 pins the pipeline to one release. Without it you get whatever the default branch happens to be on the day you run, which is the opposite of reproducible. 3.12.0 is the current release as this is written — check the releases page for a newer one, but if you do change version, change it everywhere and rerun the test, because parameters occasionally move between releases.

The first time, this also downloads the pipeline itself and its containers, so it will spend several minutes apparently doing nothing. Then you should see a process list that fills in as work completes:

[85/6b7739] NFCORE_SAREK:SAREK:PREPARE_GENOME:BWAMEM1_INDEX (genome.fasta) [100%] 1 of 1 ✔
[22/cf54a8] NFCORE_SAREK:SAREK:PREPARE_GENOME:GATK4_CREATESEQUENCEDICTIONARY [100%] 1 of 1 ✔
...

Read that line. [85/6b7739] is the start of the hash of the directory where the task ran — you will need it in a moment. The name tells you which workflow, subworkflow and process it belongs to. 1 of 1 ✔ is how many tasks of that process have finished.

Tip

With default parameters the test profile runs preprocessing and calls variants with Strelka. It is small, but it is not instant. While it runs, carry on with Step 3 in a second terminal rather than watching the progress bar.

NoteIf the test fails

Work through this in order — it is almost always one of these:

  1. nextflow: command not found — the module is not loaded in this shell.
  2. Java heap errors — NXF_OPTS is not set.
  3. Container pull errors or “no space left on device” — the cache variable is not set, or your quota is full. Check where you are with pwd; you should not be in /home.
  4. Jobs fail immediately with a permission error — you are probably trying to use Docker. Use -profile test,singularity.

If none of these is it, read Step 3 and then ask us.

Step 3: what Nextflow leaves behind

This is the part of the session with the longest shelf life. Every Nextflow pipeline you ever run will fail at some point, and the debugging procedure is always the same.

Each task runs in its own directory under work/, named by that hash you saw in the console. Go into one:

cd work/85/6b7739*     # tab-completion is your friend here
ls -a

You will find:

File What it is
.command.sh The actual command that was run. Human-readable. Start here.
.command.log Everything the tool printed
.command.err Standard error — the error message lives here
.command.run The wrapper Nextflow built, including the container and SLURM settings
.exitcode The exit status. 0 means success.

The method for any failed process: Nextflow prints the work directory of the failure, you cd into it, read .command.err, and if that is not enough, run bash .command.sh by hand and watch it break. There is no magic in a pipeline — it is a shell command in a directory.

After the run, look at the reports Nextflow wrote:

ls test_results/pipeline_info/

The execution report tells you how long each process took and how much memory it actually used, which is how you make sensible resource requests for the real run.

Important

If a run stops and you fix the problem, relaunch with -resume (one hyphen):

nextflow run nf-core/sarek -r 3.12.0 -profile test,singularity --outdir test_results -resume

Nextflow then reuses every task whose inputs have not changed and continues from the failure. Without -resume you start from the beginning, which on real data can cost you a day. Note that it matches on file content, not just filenames, and that it only works if you relaunch from the same directory, with the same work/.

Step 4: making it use the cluster

So far every task has run wherever you launched Nextflow. That is fine for a test dataset and completely wrong for real data — it would mean running an alignment on the login node.

What we want is for Nextflow itself to be a small, patient process that submits each task to SLURM as its own job. That takes a config file. Create hpc2n.config next to your run directory:

params {
    project = 'hpc2nXXXX-YYY'
}

process {
    executor       = 'slurm'
    clusterOptions = "-A ${params.project}"
    resourceLimits = [ cpus: 28, memory: 128.GB, time: 24.h ]
}

singularity {
    enabled    = true
    autoMounts = true
}

and add it with -c:

nextflow run nf-core/sarek -r 3.12.0 \
    -profile singularity \
    -c hpc2n.config \
    --input samplesheet.csv \
    --outdir results
Warning

-c is for infrastructure only — executor, resources, container settings. Do not put pipeline parameters (--input, --outdir, --tools) in a -c config file; nf-core pipelines will either ignore them or fail in a confusing way. Parameters go on the command line or in a -params-file.

NoteWhy not an institutional profile?

nf-core maintains ready-made configurations for many clusters, loaded with -profile <institution>. There is a naiss profile, but at the time of writing it only configures Arrhenius specifically, so we write our own small config for Kebnekaise instead.

The resourceLimits values above are a starting point, not a measurement. Check them against the node sizes in HPC2N’s documentation, and against what the execution report says your processes actually used.

Nextflow has to keep running for as long as the pipeline does, which can be many hours. Two ways to survive losing your connection:

# Option 1: a tmux session on the login node, detach with Ctrl-b d
tmux new -s sarek

# Option 2: let Nextflow detach itself and write to a log
nextflow run nf-core/sarek ... -bg
Tip

The Nextflow process itself uses very little CPU — it waits for SLURM — so running it on a login node inside tmux is accepted practice. It is the tasks that must go to compute nodes, and the config above is what sends them there.

Step 5: our own data

Important

The paths below are placeholders — the directory holding the subset reads will be given to you in the room. The accessions and the structure are real, and are what you should learn.

The samplesheet

Sarek takes a CSV with one row per sample and lane. Each of our eleven trees was sequenced in a single run, so there is one row per tree:

patient,sex,status,sample,lane,fastq_1,fastq_2
SAMEA104151691,NA,0,SAMEA104151691,ERR2026087,/proj/.../ERR2026087_1.fastq.gz,/proj/.../ERR2026087_2.fastq.gz
SAMEA104151857,NA,0,SAMEA104151857,ERR2026104,/proj/.../ERR2026104_1.fastq.gz,/proj/.../ERR2026104_2.fastq.gz
SAMEA104151870,NA,0,SAMEA104151870,ERR2026113,/proj/.../ERR2026113_1.fastq.gz,/proj/.../ERR2026113_2.fastq.gz
SAMEA104151879,NA,0,SAMEA104151879,ERR2026254,/proj/.../ERR2026254_1.fastq.gz,/proj/.../ERR2026254_2.fastq.gz
Column What we put in it
patient The BioSample accession. Sarek groups samples by patient; here each tree is its own “patient”
sex NA. Only used for copy-number analysis in tumour/normal pairs, and meaningless for a monoecious tree
status 0, meaning normal. There are no tumours in a birch
sample The accession again
lane The run accession. Rows for the same sample with different lane values are merged, so using the run accession here documents where each file came from
fastq_1, fastq_2 Absolute paths to the gzipped read files

Use absolute paths. Write the remaining seven rows yourself from the table at the top of this page — it is five minutes of careful typing, and getting a samplesheet wrong is the single most common reason an nf-core run fails on the first attempt.

Tip

Check your samplesheet before you launch, not after:

# Does every file in the samplesheet actually exist?
cut -d, -f6,7 samplesheet.csv | tail -n +2 | tr ',' '\n' | xargs -n1 ls -l

# Eleven samples, eleven rows plus a header?
wc -l samplesheet.csv

Nextflow will tell you about a missing file eventually, but it is more pleasant to find out in two seconds than twenty minutes into a run.

Pointing it at the reference

Sarek defaults to human reference bundles. For birch we switch that off entirely and give it the FASTA described above:

--genome null --igenomes_ignore --fasta /proj/.../dhBetPend1_two_chromosomes.fasta

The FASTA is the only reference file that is required; Sarek builds the index, the .fai and the sequence dictionary itself. Be sure it is the assembly the reads were subset against — a reference whose sequence names do not match the reads produces an empty or nonsensical result rather than an error.

Putting it together

Rather than a very long command line, write a parameter file, params.yaml:

input: '/proj/nobackup/<course-project>/<your-folder>/samplesheet.csv'
outdir: '/proj/nobackup/<course-project>/<your-folder>/results'
genome: null
igenomes_ignore: true
fasta: '/proj/nobackup/<course-project>/<your-folder>/reference/dhBetPend1_two_chromosomes.fasta'
tools: 'haplotypecaller'
joint_germline: true
skip_tools: 'baserecalibrator'

and launch:

nextflow run nf-core/sarek -r 3.12.0 \
    -profile singularity \
    -c hpc2n.config \
    -params-file params.yaml \
    -resume
NoteWhy those last three parameters
  • tools: 'haplotypecaller' — GATK HaplotypeCaller is the general-purpose germline caller. Strelka, the default in the test profile, is tuned for human data.
  • joint_germline: true — calls all eleven trees together and gives one multi-sample VCF instead of eleven separate ones. This is what we open tomorrow morning, and it is the only form in which the questions we care about can even be asked: allele frequencies, Fst and population structure are all comparisons between individuals, and a per-individual VCF cannot express them.
  • skip_tools: 'baserecalibrator' — base quality score recalibration needs a trusted set of known variants to tell real variation from sequencing error. For human data that is dbSNP. For birch no such set exists, so recalibration would be trained on our own candidate variants, which is circular. Switch it off.
Tip

Each of these is one row of the table in A human pipeline on a non-model organism. When you write the parameter file, be able to say out loud why each line is there. A parameter you copied without understanding is a result you cannot defend.

Before we stop

TipWrite down what you ran

Before you leave, note the pipeline version (-r 3.12.0), the exact command, and the Nextflow run name — the two random words it prints at startup, like focused_darwin. You can get it back later with nextflow log.

This is the minimum you need to be able to say, in a methods section, what you actually did. The course dataset was chosen partly because the original authors did this well.
